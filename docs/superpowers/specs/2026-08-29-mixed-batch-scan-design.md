# 混合目标批量检查设计

## 目标

让用户在一个批次中混合提交网站地址、公开 GitHub 仓库和本地 ZIP，后台逐个执行检查，网页关闭或刷新后任务仍继续，单项报告可单独下载 Markdown。

## 范围与约束

- 批次默认串行执行，同一时间最多一个 Strix 进程。
- 继续使用现有 Runner、Docker 沙箱、AI 模型和 7 天报告保留策略。
- 现有单目标 `POST /v1/scans` 接口保持兼容。
- ZIP 仍使用现有大小、条目数、路径穿越和符号链接校验。
- 批量输入只接受网站、公开 GitHub 仓库和 ZIP；不在本次增加私有仓库 OAuth。

## 用户流程

1. 用户打开“批量检查”，点击“添加目标”。
2. 每一行选择网站、GitHub 或 ZIP，并填写地址或选择文件。
3. 用户确认授权后点击“开始批量检查”。
4. UI 创建批次并显示总进度、当前项和每项状态。
5. Runner 持久化批次，按顺序创建单项扫描；当前项结束后自动进入下一项。
6. 完成或发现问题的项目显示 Markdown 下载按钮；失败项目显示安全的错误摘要。

## 后端设计

新增 `BatchJob` 和 `BatchItem` 持久化记录，放在现有 `runner-state` 目录。批次记录包含批次 ID、创建时间、状态、项目总数和完成数；项目记录包含输入类型、脱敏后的目标、顺序、状态、当前阶段和关联的单项扫描 ID。

新增批次 API：

- `POST /v1/batches`：校验项目列表和授权，创建批次并返回批次 ID。
- `GET /v1/batches`：返回最近批次及项目状态。
- `GET /v1/batches/{id}`：返回批次详情和项目进度。
- `POST /v1/batches/{id}/cancel`：停止当前项目并取消尚未开始的项目。

ZIP 先通过现有 `/v1/uploads` 上传，批次项目只保存 upload ID，不保存原始文件内容。批次调度器复用 `ScanManager` 的单项执行和报告逻辑；不允许绕过单项并发保护。Runner 重启时从持久化状态恢复：正在执行的项目标记失败并继续队列，等待项目保持等待状态。

## 前端设计

在现有检查入口旁增加“批量检查”入口和目标列表。目标行可新增、删除、上下移动；ZIP 行支持多选文件后展开为多个项目。开始后锁定输入列表，显示“第 N / 总数”、当前项目名称、四阶段进度和整体完成比例。历史区域增加批次摘要，仍沿用现有单项报告 Markdown 下载。

UI 通过 `runner-client.mjs` 调用批次 API，轮询批次详情；刷新后先读取批次列表，再恢复轮询。接口错误只显示安全消息，不展示 token、服务器路径或完整日志。

## 错误与取消

- 空列表、超过批次上限、无效 URL、未选择 ZIP 或未确认授权时拒绝创建。
- 单项失败记录错误码和简短消息，调度器继续下一项。
- 取消只影响当前批次：当前项发送停止信号，等待项标记为取消；已完成报告保留。
- 批次完成状态按项目结果计算：全部完成为完成，存在发现为发现问题，全部失败或取消才为失败/已取消。

## 测试

- Runner：批次创建、顺序调度、单项失败后继续、取消、重启恢复、持久化和报告关联。
- API：鉴权、输入校验、批次状态和错误响应。
- UI：混合目标提交、ZIP 多选展开、轮询恢复、下载按钮和失败提示。
